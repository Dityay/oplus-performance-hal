# Porting notes — OplusPerf

Working log for the C++ → Rust rewrite of the Performance HAL. The README is
the durable description; this is what actually happened, including the mistakes
worth remembering.

## Where the spec came from

Four sources, each covering what the others could not:

1. **The shipped service binary** (`re/original/vendor-oplus-hardware-performance-V1-service`)
   and its backend (`...-V1-ndk_platform.so`). The `BpPerformance::*` transact
   calls gave the exact method order 1..169; the stripped symbols gave the
   parcelable field types and orders. Method names are unrecoverable from a
   stripped binary except through the mangled backend, which is why
   `re/method_order.txt` is 27 KB of demangling.
2. **`re/kernel_nodes_sweep.txt` / `re/kernel_nodes.txt`**: which OPlus nodes
   actually exist on this kernel (almost none) and which MTK nodes stand in.
3. **`re/kernel_nodes_equiv.md`**: the per-method equivalence table, every MTK
   path confirmed on device 102562537K104189 before it was written down.
4. **The C++ reconstruction** (`src/PerfHal.cpp`, 1327 lines, generated by
   `scripts/gen_service_remap.py`). It was written first as a proof that the
   surface could be implemented at all, then ported; it stays in the tree as
   the record.

The `Acm*` methods and `getOswapVersion` are constants: the OPlus compact
memory manager and oswap concepts do not exist on this kernel, and the stock
service's answers are fixed. `getOswapVersion` returns -1, matching stock;
the `Acm*` group returns 0.

## The two mistakes the arg-shape test caught

`hal.rs::read_args` maps a transaction code to the in-parameters it has to
consume before dispatch. It was written by hand the first time, and the hand
copy drifted from the AIDL in two places:

- **code 82** (`readIomonitorInfo(String)`) was missing from every arm. It
  would have been parsed as "no parameters", so the reply would have been
  written against a parcel the client never laid out that way.
- **code 33** (`getDevinfoUfsVersionInfo()`, no parameters) was listed under
  the `String` arm. It would have consumed one int32 that was never sent,
  and every later transaction on that connection would then be misaligned.

Both are invisible by inspection — the arms all look plausible — which is why
`arg_arm_cover_exactly_matches_the_aidl_signatures` re-parses the AIDL file at
test time and compares the signature set to the union of the arms, in both
directions. The AIDL file is the contract; the arms are the copy. When the two
disagree, the test fails and says which code.

The same applies to the node table:
`table_matches_the_aidl_declaration_order_exactly` re-parses the AIDL and
compares all 169 names in order. That caught nothing (the table had been
generated by the same script that wrote the AIDL), but it pins the order
against future edits — a reordered table builds clean and answers every call
with the wrong method.

While writing those tests I also got the anchor indexes in a spot-check test
wrong three times in a row (`readVersion` at 107, then 165, then 121 — it is
114). The lesson was not about the anchors; it was that hand-maintained indexes
in a test are a liability. The anchors now have the full-order comparison test
next to them doing the real work.

## `ProcMemStat` has a nullable trailing int

The parcelable comment in the reconstructed AIDL says it: the shipped writer
finalises the 18th int via `getDataPosition`/`setDataPosition`, which is the
NDK idiom for a nullable primitive — value plus present flag. The naive
"17 ints and done" parse leaves a byte unconsumed and misaligns the next
element in the array.

The wire layout is therefore 20 int32s, a String, a bool, a byte, and one more
bool at the end:

```
pid, swap, pss, uss, sharedClean, sharedDirty, privateClean, privateDirty,
swapPss, anonRss, fileRss, shmemRss, gpu, kernel, dmabuf —
```

No. Actual order, from the shipped serializer: `int32 pid`, `String comm`,
`boolean isForeground`, `char oomAdj`, then the 16 numeric fields, then
`int32 reserved` and `boolean reservedPresent`. The round-trip test in
`parcelables.rs` pins this against drift on either side.

`char` in AIDL is a single byte with 3 bytes of padding, which the host codec
in `parcel.rs` reproduces. Getting that wrong (writing 4 bytes) shifts every
subsequent field by 3 and the round-trip test fails immediately — which is
why the host codec exists at all.

## `smaps` prefix matching

`sum_smaps_field` matches `Rss:` against a line like `Rss:                 120 kB`.
The trap is that `Pss_Anon:` shares a prefix with `Pss:` if the colon is left
off the key. Every key in `SMAPS_FIELDS` includes its colon, and
`sum_smaps_field(ROLLUP, "Pss:")` is asserted to be 100, not 180, in the tests.

## The statm fallback is load-bearing

The C++ comment says the HAL's SELinux domain is denied per-process smaps.
That was not verified from a denial log here; it came from the fact that the
shipped C++ has a three-level fallback at all (smaps_rollup → smaps → statm)
and from the stock service running as `user root, group system readproc` with
`SYS_PTRACE`, which would be pointless if smaps were directly readable.
The statm path computes RSS in pages × page size and reports PSS as 0. It is
kept for the same reason the shipped code has it.

`page_kib()` asks `sysconf(_SC_PAGESIZE)` rather than assuming 4 KiB, so a
16 KiB-page kernel reports a quarter of memory rather than four times it.

## Why the dispatch is table-driven

The first draft had 169 match arms. Reviewing it was impossible: each arm
reads two or three values and calls one function, and the only difference
between 40 of them is the node list. The table-driven version has one match
on the operation kind and the node lists live in `nodes.rs`, where they can be
enumerated, counted and compared against the AIDL.

The cost is that the in-parameter shapes cannot be derived from the table —
AIDL does not write a method's signature into the transaction — so `read_args`
stays hand-maintained. That is exactly the surface the two AIDL-comparison
tests exist to check.

## Build characteristics

- `DT_NEEDED`: `libdl.so liblog.so libc.so libbinder_ndk.so`. No libc++.
- 411 KB, versus the shipped C++ service's ~1.4 MB including its backend lib.
- Consecutive clean builds: identical sha256
  (`038bc0166ce9e11d187c5ccaa6eb216ebb82e5234de23256d604c0c9580ab7f0`).
- Pinned toolchain 1.99.1.

## What is not verified

- No device run of this binary. The node equivalence table was verified on
  device during the C++ phase (`re/kernel_nodes_equiv.md`), but the Rust
  service itself has not been started.
- The `Tmemory*` group targets `/sys/tmemory/`, which does not exist on this
  kernel. The methods are wired and return the documented defaults; whether a
  Transsion kernel exposes them is untested.
- `readStorageFeature`/`writeStorageFeature` use hardcoded `/proc/fs/ext4/dm-11`
  and `/sys/fs/f2fs/dm-39`, copied from the shipped C++ without remapping.
  The block device names on this device may differ.
